Some see this as a simple topic, others have never configured it due to an incomplete mastery of the techniques required to design and optimize queries effectively. This article dissects the fundamentals of parallelism using SQL Server as a base, introducing deep concepts such as parallel scans and seeks, workers, threads, tasks, execution contexts, and activity coordinators called Exchange Operators.

Systems often considered to have a strictly transactional workload (OLTP) contain queries and procedures that could benefit enormously from the appropriate use of parallelism. Extracting the maximum from this feature requires a deep understanding of how scheduling, query optimization, and the execution engine actually work.

1.

The Internals of Parallelism

The core concept of parallelism is to divide a task among a number of 'people' (processors) so that the total time required is reduced. If you needed to count 3,027 candies in a jar at a rate of five per second, it would take more than ten minutes. However, if you and four friends sit around a table, sharing a single scoop to grab candies on demand, the same task can be completed simultaneously in about two and a half minutes. This task is perfect for parallelism, as each individual is capable of working concurrently and independently.

In the database, instead of counting candies, we ask the engine to count rows in a table. For small tables, SQL Server will use a serial execution plan, using only a single worker (thread). The Stream Aggregate operator will count the rows received from the Index Scan. But if the table is large enough, the optimizer will choose to enlist additional workers, creating a parallel execution plan.

{% figure "/images/plano_paralelo.png", "Plan with parallel operators", "The plan features parallelism indicators" %}

These small yellow arrow icons in the plan identify operations involving multiple workers. Conceptually, parallel execution functions like SQL Server running multiple serial plans concurrently. The number of additional workers SQL Server assigns at runtime for each parallel region is known as the Degree of Parallelism (DOP), which is chosen right before the query starts and is determined by the number of logical processing units visible to the database.

2. Parallel Page Supplier: On-Demand Management

SQL Server does not adopt a static approach by dividing rows equally among threads, as that would make the false assumption that every row requires the same effort and that every query receives an equal share of resources.

Instead, it uses a Storage Engine feature called the Parallel Page Supplier to distribute rows among workers on demand.

  • The Parallel Page Supplier responds to requests by delivering a batch of rows to any worker that needs more work.
  • If a worker is slow, it will simply make fewer requests and process fewer rows, allowing the other workers to continue operating at their maximum rates.
  • This demand-based scheme ensures resilience against variations in worker throughput, preventing performance from being bottlenecked by the slowest worker.
  • It is triggered whenever multiple workers cooperatively read a data structure, whether a heap, a clustered table, or an index (acting in scan or seek operations).

3. Schedulers, Threads, and Execution Contexts

To avoid having to create new separate connections for each parallel query, the engine orchestrates this complexity using physical and logical abstractions.

  • Schedulers: A scheduler represents a logical processor, giving SQL Server precise control over its own thread scheduling, ensuring that only one cooperative thread is executable at a time.
  • Workers (Threads): An abstraction representing an operating system thread (or fiber), which remains bound to a specific scheduler throughout its lifetime.
  • Tasks: Represent a unit of work scheduled by SQL Server to be executed by a single worker.
  • Execution Contexts: The structural environment where the task takes place. SQL Server creates execution contexts by populating runtime details, such as references to temporary tables and variable values. The primary execution context, called context zero, is processed by thread zero, assuming the special role of 'coordinator'.
{% figure "/images/hierarquia_execucao_paralela.png", "Parallel execution hierarchy: from DOP to scheduler, worker, task, and execution context", "The chain of abstractions from DOP to execution context" %}

4. The Exchange Operator: The Glue

The final and most vital ingredient in a parallel plan is the Exchange Operator. It acts as the "glue" connecting execution contexts, being the only operator in the plan that interacts directly with more than one worker.

Logically, the Exchange Operator appears in three forms:

  • Gather Streams: Consolidates flows from multiple threads into one.
  • Distribute Streams: Takes an input stream and spreads it across multiple threads.
  • Repartition Streams: Redistributes rows across interfaces between two parallel regions.
{% figure "/images/exchange_operator_tipos.png", "The three logical forms of the Exchange Operator: distribute streams, repartition streams, and gather streams", "The three logical forms of the Exchange Operator" %}

The Internal Design of Exchange

Physically, this operator is subdivided into Producers (which connect to input workers, packing rows into memory buffers) and Consumers (which connect to output workers, reading rows from these buffers when requested). The use of in-memory buffers implements flow control to prevent fast producers from outpacing slow consumers.

{% figure "/images/exchange_producer_consumer.png", "Physical structure of the Exchange Operator: producers, in-memory buffer, and consumers", "Producers and Consumers connected by in-memory buffers" %}

Data Routing (Partitioning Types)

To determine which consumer receives each row, the Exchange uses five partitioning strategies:

  • Hash: The consumer is chosen by executing a hash function on one or more column values of the row.
  • Round Robin: Each new row is sent to the next consumer following a fixed sequence.
  • Broadcast: Each input row is sent entirely to all consumers simultaneously.
  • Demand: The row is sent to the first consumer that requests it.
  • Range: Each consumer receives an exclusive, non-overlapping range of values.
{% figure "/images/particionamento_exchange.png", "The five partitioning strategies of the Exchange Operator: hash, round robin, broadcast, demand, and range", "The five Exchange data routing strategies" %}
Order Preservation: Exchange operators can also be configured to preserve input ordering. Known as merging exchanges and identified by the Order By attribute, they perform no physical sorting; they are strictly limited to preserving the exact sort order with which the rows arrived at their inputs.
