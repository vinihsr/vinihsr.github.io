This article describes a fundamental step for the SQL Server DBA: adapting to the Linux environment. Whether to lower operating system licensing costs, standardize pipelines with containers, or unify a server stack, understanding how to manage the SQL Server engine outside its natural habitat is vital.

With that in mind, let's start with the reality check: leaving the comfort of Windows Server.

In the PostgreSQL ecosystem, Linux is the native home. Postgres DBAs are accustomed to managing processes, analyzing memory consumption, and troubleshooting I/O directly via the terminal. For SQL Server DBAs, who historically depend on Task Manager, PerfMon, and SSMS for everything, the black screen can feel hostile. But the concepts are the same; only the tools change.

When a server experiences slowdowns, the first reaction on Windows is to open the Task Manager. On Linux, we access the terminal and use native tools that read information directly from the kernel.

1.

CPU and Memory (The Task Manager Replacement)

For real-time process monitoring, the classic command is top (or htop, its enhanced, interactive version). It provides a view of CPU consumption per core, RAM usage, and Swap. For SQL Server, you'll look for the main process named sqlservr.

{% codeblock "bash" %} # Opens the interactive process monitor. Press 'F4' to filter by 'sqlservr' and 'q' to exit. htop {% endcodeblock %}

If you need a quick, static overview solely of global RAM memory consumption (total, used, free, and cached/buffered), the free command is the right choice:

{% codeblock "bash" %} # Displays system memory usage in a human-readable format (Megabytes/Gigabytes) free -h {% endcodeblock %}

2. Storage and I/O (The Windows Explorer and Resource Monitor Replacement)

Unlike Windows with its C:, D:, and E: drives, Linux uses a unified directory tree mounted at the root (/). To check free disk space, we use df -h. To find out the size of a specific folder (such as database files), we use du -sh.

{% codeblock "bash" %} # Checks free space across all mounted partitions df -h # Checks the total size of the default SQL Server data directory sudo du -sh /var/opt/mssql/data/ {% endcodeblock %}

But for a DBA, free space isn't enough; we need to see read and write bottlenecks (I/O). iostat is essential for measuring IOPS and disk latency during slowdowns:

{% codeblock "bash" %} # Displays extended disk I/O statistics, refreshing every 2 seconds iostat -xd 2 {% endcodeblock %}
Fun fact: Microsoft kept the logical structure so faithful that data files continue to be .mdf, .ndf, and .ldf, even running on an ext4 or XFS file system on Linux.

3. Services and OS Logs (The services.msc and Event Viewer Replacement)

In modern Linux, background services (daemons) are managed by systemd. Instead of opening graphical panels to restart the database service, everything is done via systemctl. And to read logs recorded by the OS (in case the service crashed before SQL even started), we use journalctl.

{% codeblock "bash" %} # Checks whether SQL Server is running, failed, or inactive sudo systemctl status mssql-server # To forcefully restart the SQL Server service sudo systemctl restart mssql-server # Reads the last 50 system logs generated specifically by SQL Server sudo journalctl -u mssql-server -n 50 {% endcodeblock %}

4. Reading Internal Logs and Files (The Notepad / SSMS Log Viewer Replacement)

On Windows, you would open SSMS or Notepad to analyze the famous SQL Server ERRORLOG. On Linux, we read giant text files instantly via the terminal without freezing. tail reads the end of the file, while grep acts like a "Ctrl+F", searching for specific snippets.

{% codeblock "bash" %} # Displays the last lines of the ERRORLOG in real-time (following live writes) tail -f /var/opt/mssql/log/errorlog # Searches exclusively for login failures (Login failed) inside the ERRORLOG grep "Login failed" /var/opt/mssql/log/errorlog {% endcodeblock %}

5. Network and Connectivity (The Windows netstat Replacement)

The application can't connect? Before blaming the database, you need to verify if SQL Server actually started up and is listening on the correct port (1433 by default). The ss (Socket Statistics) command replaces netstat.

{% codeblock "bash" %} # Lists open TCP ports (Listening), numerically, and shows which process is using them sudo ss -tlnp | grep sqlservr {% endcodeblock %}

How does SQL Server on Linux work under the hood?

Here we need to address a crucial point. Unlike PostgreSQL, which was written with direct calls to native Linux kernel APIs (POSIX), the SQL Server relational engine contains millions of lines of code heavily tied to Windows APIs (Win32).

Microsoft did not rewrite SQL Server from scratch. They created a brilliant abstraction layer called SQLPAL (SQL Server Platform Abstraction Layer). Based on the older research project Drawbridge, SQLPAL acts as a "mini operating system" embedded inside the Linux process. It translates calls from the database engine in real time into calls that the Linux kernel can understand.

  • Full Compatibility: Thanks to SQLPAL, the engine continues to use the same scheduling structures (SQLOS). The database "thinks" it is on Windows.
  • Transparent Migration: Because of this architecture, you can take a backup (.bak) on a Windows Server 2022 and restore it perfectly on a Linux server.

Installation and Tools: No Graphical Interface

If you've used Linux in your life, here is the biggest conceptual difference: on Windows, you go to Microsoft's website, download a multi-gigabyte .iso file, mount the image, and run a setup.exe. On Linux, we use Package Managers (such as apt on Ubuntu or dnf on RedHat).

Instead of hunting down a file, you tell the operating system via the terminal where Microsoft's servers are located, and Linux itself downloads, unpacks, and installs everything in the right place. This makes life easier for anyone working with automation (Ansible, Terraform) and Infrastructure as Code.

Using Ubuntu as an example (the most beginner-friendly distribution), the physical process boils down to these commands:

{% codeblock "bash" %} # 1. Imports Microsoft's security key (to ensure the download is official) curl -fsSL https://packages.microsoft.com/keys/microsoft.asc | sudo gpg --dearmor -o /usr/share/keyrings/microsoft-prod.gpg # 2. Adds the SQL Server 2022 repository to your Linux "phonebook" curl -fsSL https://packages.microsoft.com/config/ubuntu/22.04/mssql-server-2022.list | sudo tee /etc/apt/sources.list.d/mssql-server-2022.list # 3. Updates the list of available packages and installs the database engine sudo apt-get update sudo apt-get install -y mssql-server {% endcodeblock %}

Done, the binaries are installed. But the database is not running yet. The final configuration is missing (collation, ports, and the famous SysAdmin password). For this, Microsoft created an exclusive utility called mssql-conf.

{% codeblock "bash" %} # Runs the interactive initial configuration wizard sudo /opt/mssql/bin/mssql-conf setup {% endcodeblock %}

When running the command above, the terminal will ask you two crucial questions:

  1. The SQL Server Edition: It will list options from 1 to 8 (Evaluation, Developer, Express, Standard, Enterprise...). Type the number corresponding to your need and press Enter.
  2. The sa Password: Here is a detail that every beginner on Linux gets confused by: for security reasons, when typing passwords in the terminal, nothing appears on screen. Not even asterisks. Linux is capturing the keystrokes. Just type your strong password and press Enter.

What about day-to-day administration?

SSMS is wonderful, but it is exclusive to Windows. For a cross-platform workflow, we have two primary options:

  • Azure Data Studio (ADS): This is the modern recommendation. Built on Electron (the same base as VS Code), it runs natively on Linux. It has excellent support for T-SQL, graphical execution plan visualization, and powerful extensions.
  • DBeaver: Java-based, it is an extremely popular universal client in the Linux community. If you manage multiple database engines in your day-to-day work, it connects seamlessly to SQL Server (via JDBC driver) and offers a robust, familiar graphical interface that strongly resembles the structural flexibility of SSMS.
  • sqlcmd: The official command-line tool. Essential for when you are connected via SSH to a server without a graphical interface and need to run quick queries or maintenance scripts.
{% codeblock "bash" %} # Connecting locally via sqlcmd to test the instance sqlcmd -S localhost -U sa -P 'SuaSenhaForte123!' -Q "SELECT @@VERSION" {% endcodeblock %}

The initial learning curve might scare anyone who has never left the Microsoft ecosystem, but the fundamentals of the database engine remain the same. Mastering the Linux CLI not only expands your administration and troubleshooting portfolio, but it's the first step toward orchestrating robust databases in container-oriented architectures.
