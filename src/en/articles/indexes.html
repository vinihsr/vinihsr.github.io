What is an Index?

An index is a data structure persisted on disk, built from one or more columns of a table. Its exclusive purpose is to optimize record retrieval, minimizing the amount of disk accesses (I/O) required to locate information. Physically, the index is a separate entity from the data table it indexes.

2. Why does the database require indexes?

Without an index, the database engine is forced to perform a sequential scan. In SQL Server, this is called a Table Scan (on Heaps) or Clustered Index Scan. In PostgreSQL, it is a Seq Scan.

The sequential scan reads all table data pages from disk into RAM, evaluating the filter row by row. The mathematical complexity of this operation is O(N). By implementing an index, the engine locates data via tree traversal, reducing the mathematical search cost to O(log N). The absence of indexes on massive tables causes CPU saturation, I/O contention, and cache exhaustion.

3. Index Types and Engines (PostgreSQL vs. SQL Server)

The primary architectural difference between the two engines lies in how base data is stored. SQL Server fundamentally works with the Clustered Index (where the table is the sorted index itself at the leaf level). PostgreSQL does not have this strict concept; in Postgres, all tables are Heaps, and every index acts analogously to a SQL Server Non-Clustered Index.

Below are the indexing algorithms and engines supported by each platform:

Balanced Tree (B-Tree)

The absolute standard for daily high-concurrency transactional operations.

  • SQL Server: Used to create both disk-based Clustered and Non-Clustered indexes.
  • PostgreSQL: Default engine when the type is omitted in the CREATE INDEX declaration.

Engines for Large Volumes and Analytical Queries

When balanced trees become inefficient for multi-terabyte tables, engines adopt distinct strategies:

  • SQL Server (Columnstore): Physical structure focused on analytical repositories. Stores data in columns (instead of rows) divided into compressed segments, drastically reducing I/O in massive aggregation queries.
  • PostgreSQL (Block Range Index - BRIN): Designed for time-series and sequentially inserted data. Instead of indexing row by row, this model stores only the minimum and maximum values of adjacent physical blocks (e.g., 1 MB ranges). It allows skipping millions of rows during reads with negligible memory consumption.

Hash Indexes

Specific for strict equality operators (=), ineffective for range searches (> or <).

  • SQL Server: Exclusive and mandatory for memory-optimized tables resident in RAM. Not applicable to classic disk-based tables.
  • PostgreSQL: Natively implemented as a disk index type supported by the default mechanism.

Complex Structures (JSON, XML, and Arrays)

Indexing internal documents and collections requires engines that understand textual or structured sub-elements.

  • SQL Server: Uses XML Indexes (structured over internal trees) and, for JSON, relies on property extraction into indexed computed columns or the Full-Text Search service, which operates as an external system process outside the classic relational engine.
  • PostgreSQL (Generalized Inverted Index - GIN): Works analogously to the back-of-book index. Capable of extracting and indexing multiple independent values within a single row, making it the definitive engine for high-performance operations on JSONB fields, two-dimensional arrays, and native text search.

Spatial and Geometric Data

  • SQL Server: Uses Spatial Indexes, based on tessellation techniques (decomposing two-dimensional space into mathematical grids).
  • PostgreSQL: Relies on the Generalized Search Tree (GiST) engine, a generic structure enabling index implementation for irregular overlapping data, such as polygons and geographic coordinates (heavily used by the PostGIS extension).

4. The Internals: Pages, Construction, and Balanced Structure

The Generic Anatomy of a Page

Both SQL Server and PostgreSQL structure table and index storage in fixed I/O blocks called Pages, which default to 8 KB in size. Although structural differences exist in the control bytes of each DBMS, generically, a page is divided into three fundamental sections:

  1. Page Header: Occupies the first bytes of the block. Contains vital metadata, such as the ID of the object the page belongs to, remaining free space, transaction markers (like log sequence numbers), and logical pointers to the previous and next pages (forming a structural doubly linked list).
  2. Data Body (Tuples/Records): The central area of the page where actual data resides and grows downward from the top. In a table page (Heap), these are table row columns. In an index page, the data body strictly contains the indexed key plus an identifier pointer to the original row.
  3. Row Offset Array: Positioned at the end of the page (footer) and grows upward from the bottom. A mapping vector storing the exact byte address where each record starts within the page. This allows the CPU to perform an ultra-fast binary search directly within the 8 KB block in RAM without scanning record by record internally.

Structure Construction (How the Index Extracts Data)

When executing a CREATE INDEX command, the index is not created by magic; it is physically built from a copy of the table's data. The database engine executes a deep read on the base table and extracts exclusively the values of the columns declared in the index, along with their respective identifier pointers. These extracted data points are allocated in RAM (sorting areas) and rigorously sorted.

With data sorted, the engine builds the tree structure from the bottom up:

  1. It populates and links the Leaf Level pages containing all sorted data.
  2. Next, it generates Intermediate Level pages, storing only the lowest value of each leaf page to act as directional "signposts."
  3. Finally, it condenses these routes to form a single Root page, the entry point for all queries.

Balanced Tree Mechanics

A perfectly distributed structure ensuring that depth (the exact distance between Root and Leaf levels) across all branches is identical. This stabilizes read response time regardless of the queried record.

  • Performance: Highly optimized for mathematical operators (<, <=, =, >=, >). Applying functions directly over indexed columns in a WHERE clause negates the engine's ability to efficiently navigate tree nodes, forcing a costly full index scan.

5. How Data and Indexes Communicate

The physical location of data requires an internal pointer to connect the index (the reduced, sorted copy) to the main table (raw, complete data). In SQL Server, a Non-Clustered index uses the Clustered index key as a pointer to locate the record in the main tree. In PostgreSQL (which fundamentally works with unsorted Heaps), the architecture uses the Physical Record Identifier.

The Physical Record Identifier

This identifier is a precise structural coordinate composed of two hardware values: (8KB Block Number, Record Position within the Block).

  1. The tree's leaf node in PostgreSQL stores the indexed key tied to its corresponding identifier.
  2. The execution engine reads the key in the index, extracts the identifier, and accesses disk by going directly to the exact page and line in the raw table to gather missing columns.

Concurrency Control and the Visibility Map

In SQL Server, record and page locks manage concurrency. In PostgreSQL, multiversion concurrency control keeps old versions of updated or deleted rows physically alive on disk to ensure reads from other transactions are not blocked.

The index in PostgreSQL does not store information regarding which transaction is permitted to see the row. Thus, even in a scenario where a query requires only columns already present inside the index itself, the engine would need to physically visit the main table's page to check transaction metadata and ensure the read row was not recently deleted by a concurrent process. To mitigate this heavy disk read penalty, PostgreSQL uses the Visibility Map, a bit map indicating whether all records in a specific 8KB block are universally visible and definitive. If the bit is affirmatively flagged, the engine relies solely on data extracted from the index and bypasses visiting the main table.

6. Practical Implementation (Indexing Syntax)

The examples below demonstrate granular control in creating and maintaining these optimization structures.

{% codeblock "sql" %} -- SQL SERVER - Creating a Secondary Index with aggregated columns (Covering Index) CREATE NONCLUSTERED INDEX idx_sales_date ON Sales (OrderDate) INCLUDE (TotalAmount, CustomerID); -- POSTGRESQL - The structurally equivalent syntax to a Covering Index CREATE INDEX idx_sales_date ON sales (order_date) INCLUDE (total_amount, customer_id); -- SQL SERVER - Creating an index while keeping the table available for writes (Avoids Locks) CREATE INDEX idx_customers_status ON Customers (Status) WITH (ONLINE = ON); -- POSTGRESQL - Equivalent syntax for creation without requiring exclusive table locking CREATE INDEX CONCURRENTLY idx_customers_status ON customers (status); -- POSTGRESQL - Creating a Generalized Inverted Index for JSONB field structuring CREATE INDEX idx_products_attributes ON products USING GIN (attributes_jsonb); -- SQL SERVER - Creating a Columnstore Index for massive read volumes of large datasets CREATE NONCLUSTERED COLUMNSTORE INDEX idx_cs_analytics ON FactTable (DimDate, MeasureValue); -- POSTGRESQL - Creating a Block Range Index for time-series records CREATE INDEX idx_sensor_metrics ON sensor_data USING BRIN (recorded_timestamp); {% endcodeblock %}
