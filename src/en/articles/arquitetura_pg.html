Previously, we covered SQL Server's architecture: driver, parser, binder, plan cache, optimizer... Now, riding that momentum, we will discuss PostgreSQL — besides documenting another database management system, we will take what we captured from SQL Server and reuse it here, filling knowledge gaps with what differs and seeking to understand what it's all about.

This article covers everything from connection to query execution — the "architecture and specification" side of the engine. Locks, MVCC, and VACUUM are left out of this article because they are lengthy subjects, and the focus here is to understand how the engine works, how a query enters and exits, without major specifications. After all, the aforementioned topics are extensive and deserve their own dedicated article, as they belong, in my view, to the management context rather than core architecture.

In SQL Server, your application talks to a driver that maintains a connection pool inside the client itself. In PostgreSQL, the logic of "who handles the connection" is different: there is no native pooling inside the driver. Every new connection is received by the Postmaster, the parent process listening on port 5432 (default), and it responds by creating a fork — a brand new operating system process dedicated exclusively to that session from start to finish.

If you don't use any external pooling tool (PgBouncer, pgpool, or application-level pooling), every new connection pays the cost of a fork. If you do, the tool holds a set of pre-opened connections with Postgres and hands one of them to your application without going through the Postmaster again — but if the pool has no free connection at that moment, it will still request a new fork. Pooling reduces fork frequency; it doesn't eliminate it. But between always paying and—depending on good configuration—paying much less, using an external tool is always the ideal choice.

Fun fact: this is the most fundamental architectural difference between the two databases, and it propagates to everything that follows. SQL Server uses threads inside a single process, coordinated by SQLOS, the engine's own scheduler. PostgreSQL uses one OS process per connection. This explains why "many simultaneous connections" is a much more serious scaling problem in Postgres — every idle connection still consumes OS process memory, not just a lightweight thread — and why external pooling tools are considered mandatory infrastructure in production, not an option.

From here, the query has physically arrived at the backend process dedicated to it. This is where PostgreSQL's internal architecture takes over.

Past the connection, we enter the real engine: the Parser

Just like in SQL Server, the first stage is a purely syntactic check. Postgres's Parser doesn't know if the table exists, it doesn't know if the column exists — it only verifies whether the SQL is written in a way that makes grammatical sense, following the formal grammar of the system's dialect.

If you've ever received an error like syntax error at or near..., that was the parser complaining. Same logic as SQL Server: cheapest phase, fastest phase, and syntax errors are never a performance problem.

After syntax comes the real check: Parse Analysis

This step is the direct equivalent of SQL Server's Binder/Algebrizer. It resolves names — does the table public.pedidos exist? does the column cliente_id exist in it? — and types: can this integer column be compared to this text parameter? This is where errors like relation "pedidos" does not exist or column "cliente_id" does not exist appear.

Fun fact: implicit type conversions happen here, with the same consequence as in SQL Server — loss of SARGability. A WHERE coluna::text = $1 can push the planner toward a Seq Scan where an Index Scan would be possible, for the exact same reason that a poorly placed CONVERT() kills an index seek in SQL Server. The root of the problem is identical in both engines: the index is built on the column's original type, and a conversion along the way prevents the optimizer from matching the WHERE expression with that index.

A new stage (for SQL Server DBAs): the Rewriter

After Parse Analysis, Postgres goes through a proprietary stage called the Rewriter, which consults the rules stored in the system catalog. The most common application of this, and the one you will encounter day-to-day, is view expansion: when your query references a view, the Rewriter replaces that reference with the actual underlying query before anything is planned. SQL Server resolves views more directly inside the binder/optimizer itself; Postgres treats this as a separate and explicit query rewrite stage.

Before thinking, the engine decides: do you have a PREPARE?

Here lies the biggest behavioral difference between the two databases, which, despite its complexity, works well: PostgreSQL does not have an automatic plan cache. There is no global cache holding plans for queries arriving via the simple protocol. Every "loose" query — without a PREPARE — is parsed, rewritten, planned, and executed from scratch, and the plan is discarded right after. There is no soft parse here; without PREPARE, it is always a hard parse (terms borrowed from Oracle, but in more familiar language: without PREPARE, it ALWAYS recompiles!).

Plan caching only enters the picture if you use prepared statements — via explicit PREPARE name AS ..., or via the driver's extended protocol (JDBC, for example, has a configurable prepareThreshold; Node/Python drivers usually expose something similar). And even then, the behavior is smarter than a shallow cache:

PREPARE does not generate a plan. It stores the already parsed and rewritten query, but planning itself only happens when you call EXECUTE. From the first through the fifth execution, Postgres generates a custom plan on each call — replanning using actual parameter values, exactly as it would for a loose query — and calculates the estimated average cost of these plans. On the sixth execution, it generates a generic plan (without knowing future parameter values) and compares its estimated cost with the average of the custom plans. If the generic plan isn't much worse, Postgres starts reusing that generic plan from then on — without replanning. If it is significantly worse, it continues generating custom plans forever.

Fun fact: this makes Postgres's parameter sniffing adaptive, unlike SQL Server, where the plan is compiled once (based on the first execution's values) and stays locked until forced recompilation. In Postgres, if a column has highly skewed data distribution — a flag that is 99% 'Y' and 1% 'N', for example — the generic plan can be dramatically worse than the custom one because it doesn't know which value is coming. There is even a case reported on the official Postgres mailing list of a generic plan running 158,000 times slower than the equivalent custom plan. For these cases, you can force behavior with SET plan_cache_mode = 'force_custom_plan' (or force_generic_plan, if you want the opposite).

To see this behavior in action:

{% codeblock "sql" %} -- View active prepared statements for the current session: how many times each -- ran as a custom vs. generic plan SELECT name, statement, generic_plans, custom_plans, parameter_types FROM pg_prepared_statements; -- Force custom plan always in a specific session — useful for debugging -- a case where the generic plan appears to have degraded SET plan_cache_mode = 'force_custom_plan'; -- Check via EXPLAIN whether current execution is using a generic plan -- (appears with $1, $2...) or a custom plan (literal values substituted) EXPLAIN EXECUTE prepared_statement_name(value); {% endcodeblock %}

Without PREPARE or after the decision: enter the Planner

Postgres's Planner is conceptually the same type of component as SQL Server's Query Optimizer: it doesn't search for the absolute perfect plan, it searches for a good enough plan, fast enough. The process follows the same background logic — query simplification, checking for trivial cases (a direct primary key lookup doesn't need to compare alternatives), and, if non-trivial, generating candidate plans with costs estimated via statistics.

The statistics used here come from the pg_statistic catalog (exposed cleanly via the pg_stats view), populated by ANALYZE — the direct equivalent of SQL Server's UPDATE STATISTICS. Outdated statistics have the exact same consequence in both databases: wrong row estimation, wrong join choice, bad plan.

Fun fact: for queries involving many tables in joins, Postgres swaps exhaustive candidate searching for a heuristic called GEQO (Genetic Query Optimizer) — a literal genetic algorithm that evolves populations of candidate plans instead of comparing all possible combinations. SQL Server has nothing like this; it always performs deterministic searches, limited only by optimization time/cost.

With the plan decided — custom, generic, or freshly planned without PREPARE — the query proceeds to the Executor:

It runs the plan tree from bottom to top, pulling rows as needed, following the exact same conceptual approach as SQL Server. The result isn't fully assembled on the server either: it is streamed via the libpq protocol, row by row, as it is produced — matching TDS behavior in SQL Server, including the same diagnostic trap: if the client processes slowly, Postgres sits waiting for it to consume, which shows up as a ClientWrite wait — the equivalent to ASYNC_NETWORK_IO, and equally easy to mistake for a "network problem" when it isn't.

What happens inside this execution — how Postgres controls concurrency without SQL Server's pessimistic locks, why lock escalation practically doesn't exist here, and why VACUUM is an essential routine — is a large enough subject to earn a new article with its own diagram.

Keep this list in mind — it's what you should consult when trying to understand what happens between a query leaving the application and a plan being ready:

  • Active prepared statements and custom vs. generic usage: pg_prepared_statements
  • Active connections and each one's backend process: pg_stat_activity
  • Manually forcing custom or generic plans: plan_cache_mode
  • Statistics used by the planner: pg_stats, and ANALYZE to update
  • Most executed queries and time spent in parsing/planning: pg_stat_statements (with track_planning enabled)
  • Viewing the actual chosen plan for a prepared statement: EXPLAIN EXECUTE name(values)

Just like in the SQL Server article, the golden rule is: before rushing to tweak an index, understand the path the query took. In Postgres, that path has extra details that differ significantly, but they will help you understand why a database already has a good query, plan, and index, yet occasionally feels slow.
