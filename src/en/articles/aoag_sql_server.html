Hello everyone! If you work with support, architecture, or data engineering in mission-critical environments, you know that ensuring the database stays online even during hardware, network, or local disaster failures is one of the most important pillars of the profession. In the Microsoft SQL Server universe, the definitive solution to this challenge goes by the name of Always On Availability Groups (AG).

In this article, we will take a deep dive into the subject: we'll move from the concept of HADR to the internal anatomy of engine threads, compare the architecture with PostgreSQL, and wrap up with ready-to-use T-SQL scripts for your day-to-day monitoring.

1.

The Concept of HADR and Evolution: Why Always On Replaced Database Mirroring?

To understand Always On AG, we first need to review two essential acronyms in the corporate world:

  • HA (High Availability): Focuses on minimizing unplanned downtime (RTO - Recovery Time Objective close to zero).
  • DR (Disaster Recovery): Focuses on ensuring that data is not lost in the event of failures (RPO - Recovery Point Objective close to zero).

Before SQL Server 2012, the primary transaction-log-based technology for HADR was Database Mirroring. Despite being efficient for its time, it had severe limitations:

  • It operated strictly at the level of a single database per session. If your application depended on three relational databases, failing over one did not guarantee the failover of the others.
  • The secondary replica remained inaccessible for reads (unless you created a manual Database Snapshot).
  • Deprecated by Microsoft in more recent versions.

Always On Availability Groups solved these pain points by allowing multiple databases (Availability Databases) to be grouped together to fail over collectively, supporting up to 8 secondary replicas, offloaded reads (read-only replicas), backups on secondaries, and the concept of the Listener — a VIRTUAL Connection Point (VNN + IP) that transparently redirects application traffic to the current primary node.

2. Architecture Explained:

A classic question is: What happens to the physical data on the primary node after sending the log? Does it wait for secondary confirmation to write to the MDF file? The answer lies in the strict separation between the movement of Transaction Log (LDF) blocks and the writing of data pages (MDF) through the concept of Write-Ahead Logging (WAL).

The Journey of a Transaction and the Primary MDF

  1. In-Memory Modification & Log Flush (Primary): When an application submits an INSERT/UPDATE/DELETE, data pages are modified only in memory (in the primary node's Buffer Pool). Upon issuing a COMMIT, SQL Server writes this change record to the local physical log file (LDF). Attention: Physical writing to the primary data file (MDF) does NOT happen at this moment. It is entirely independent of the COMMIT or the AG, occurring asynchronously later (via Checkpoint or Lazy Writer processes).
  2. Log Capture & Log Sender (Primary): As soon as the log is written to the primary LDF, the Log Capture thread reads these new log blocks and passes them to the Log Sender thread, which transmits them over the network (TCP/IP) to the secondary replicas.
  3. Log Receive & Log Hardening (Secondary): The secondary node receives the blocks (via the Log Receiver thread) and writes them immediately to its own physical log file (secondary LDF). This crucial step is called Log Hardening.
  4. The ACK Return: It is only after Log Hardening that the secondary notifies the primary that the data is safe on disk (Acknowledge).
  5. Redo Thread (Secondary): Continuously and in the background, the Redo Thread reads blocks from the secondary LDF and applies the changes to the data pages (MDF/NDF) of the secondary replica, making the data available for reads.
The Synchronous COMMIT Waiting Point: In Synchronous-Commit mode, when the application requests a COMMIT, the primary node leaves it waiting (in the HADR_SYNC_COMMIT wait state). The application only receives a "Success" response when the primary completes its own Log Flush AND receives the Log Hardening ACK from the secondary. The primary does NOT wait for the Redo Thread to apply the data to the secondary MDF, nor does it wait for Checkpoint to write to the primary MDF.

Summary: Commit Modes

  • Synchronous-Commit Mode: The transaction waits for LDF (log) writing on both ends. Guarantees RPO = 0 (zero data loss). If the secondary slows down, application writes on the primary will experience latency.
  • Asynchronous-Commit Mode: The primary confirms the transaction to the application immediately after its own Log Flush (primary LDF). It does not wait for the secondary to receive or write anything, focusing on performance (ideal for high-latency DR links).

3. A Parallel with PostgreSQL

If you manage hybrid environments or work with multicloud, it is natural to draw bridges between market technologies:

  • Always On's transaction log transport is conceptually equivalent to PostgreSQL's Streaming Replication via WAL (Write-Ahead Logging).
  • SQL Server's Redo Thread plays a role analogous to the continuous application of WAL blocks by Postgres recovery on the Standby node.
  • Connection routing performed by SQL Server's Listener and failover control performed by the WSFC (Windows Server Failover Cluster) in Postgres are typically implemented via an open-source ecosystem with Patroni + etcd + HAProxy/PgBouncer.
Multicloud Parallel: While SQL Server orchestrates high availability quorum by delegating intelligence to the operating system cluster (WSFC on Windows or Pacemaker on Linux), the PostgreSQL ecosystem broadly adopts the Distributed Consensus model via software (DCS like etcd or Consul in Patroni) for leader election and virtual IP maintenance.

4. What is Replicated? (And What is Left Out)

A common confusion among developers and junior DBAs is treating Always On as logical replication. Unlike traditional SQL Server Transactional Replication, Always On AG operates at the physical database level.

Because it transports binary Transaction Log (LDF) blocks, absolutely everything modifying the database contained within the group is replicated. This includes:

  • Structures and Data: Creation of tables, views, and transacted data.
  • Programmability and Behaviors: Triggers (DML and DDL), Stored Procedures, Functions, and User-Defined Types (Types).
  • Performance: Creation, alteration, and rebuilding of indexes (an index REBUILD on the primary generates massive log that will be physically redone on the secondary).
Critical Difference: Instance Objects are NOT Replicated! Because the AG scope encompasses only the User Database, server-level objects do not come along for the ride. This means Logins, SQL Server Agent Jobs, Linked Servers, and Server Roles are not synchronized automatically in traditional versions. SQL Server 2022 introduced Contained Availability Groups to specifically resolve this pain point by replicating instance metadata (virtual master/msdb).

5. Complete Step-by-Step: Setting Up an AG from Scratch

To implement this architecture in a real production environment, you need to coordinate network infrastructure, operating system, and the database engine. As promised, here is the essential roadmap for DBAs, focused on what matters without relying on Wizard screens:

Phase 1: Cluster Preparation (Operating System)

  1. Make sure all servers (nodes) belong to the same Active Directory (AD) domain.
  2. Install the Failover Clustering feature on Windows Server across all participating nodes.
  3. Create the Cluster (via PowerShell or Failover Cluster Manager), joining the servers.
  4. Configure the Quorum (usually a File Share Witness or shared disk) to ensure tie-breaking and prevent Split-Brain syndrome if network connectivity between nodes drops.

Phase 2: Enabling the Feature in SQL Server

  1. Open SQL Server Configuration Manager on each node.
  2. Go to the properties of the main SQL Server service (sqlservr.exe) and select the "Always On Availability Groups" tab.
  3. Check the box for "Enable Always On Availability Groups" (the name of the WSFC Cluster created in Phase 1 will appear there).
  4. Restart the SQL Server service so the Database Engine adopts the new configuration.

Phase 3: Preparing the Database

Always On requires an intact and continuous log chain. Therefore, the candidate database must meet two strict requirements:

  1. The database's Recovery Model must be set to FULL.
  2. You must execute a FULL Backup and immediately afterwards a Log Backup of the database on the Primary server. Restore them on the Secondary with the NORECOVERY clause.

Phase 4: Creating the AG and Listener via T-SQL

Once prerequisites are validated, execute the script below on the primary node to create the group, define routing, and establish replicas:

{% codeblock "sql" %} -- 1. Create Availability Group CREATE AVAILABILITY GROUP [MeuAG_Producao] WITH (AUTOMATED_BACKUP_PREFERENCE = SECONDARY) FOR DATABASE [MeuBancoCritico] REPLICA ON 'SRV-SQL-01' WITH ( ENDPOINT_URL = 'TCP://SRV-SQL-01.meudominio.com:5022', AVAILABILITY_MODE = SYNCHRONOUS_COMMIT, FAILOVER_MODE = AUTOMATIC, SECONDARY_ROLE (ALLOW_CONNECTIONS = ALL) ), 'SRV-SQL-02' WITH ( ENDPOINT_URL = 'TCP://SRV-SQL-02.meudominio.com:5022', AVAILABILITY_MODE = SYNCHRONOUS_COMMIT, FAILOVER_MODE = AUTOMATIC, SECONDARY_ROLE (ALLOW_CONNECTIONS = ALL) ); -- 2. Create Listener (Virtual Connection Point) ALTER AVAILABILITY GROUP [MeuAG_Producao] ADD LISTENER 'LST-MEUAG' ( WITH IP (('192.168.1.100', '255.255.255.0')), PORT = 1433 ); {% endcodeblock %}

Phase 5: Joining the Secondary Nodes

Access each secondary server and instruct them to join the newly created group, initiating continuous network communication:

{% codeblock "sql" %} -- Execute on Secondary node ALTER AVAILABILITY GROUP [MeuAG_Producao] JOIN; ALTER DATABASE [MeuBancoCritico] SET HADR AVAILABILITY GROUP = [MeuAG_Producao]; {% endcodeblock %}

6. Essential Day-to-Day Monitoring Queries

SSMS visual dashboards (GUI) help with rapid diagnosis, but a Senior DBA needs precise, automated scripts via T-SQL. Below, I share two fundamental queries from my troubleshooting arsenal.

Query 1: General Synchronization State and Replica Health

This query returns the connection state, operational role, synchronization mode, and health status of each database within the Availability Group.

{% codeblock "sql" %} SELECT ag.name AS availability_group, ar.replica_server_name, d.name AS database_name, drs.role_desc AS replica_role, drs.operational_state_desc, drs.connected_state_desc, drs.synchronization_state_desc, drs.synchronization_health_desc, drs.is_local FROM sys.dm_hadr_database_replica_states drs INNER JOIN sys.availability_replicas ar ON drs.replica_id = ar.replica_id INNER JOIN sys.availability_groups ag ON ar.group_id = ag.group_id INNER JOIN sys.databases d ON drs.database_id = d.database_id ORDER BY ag.name, ar.replica_server_name, d.name; {% endcodeblock %}

Query 2: Identifying Bottlenecks and Latency (Log Send Queue & Redo Queue)

Essential for diagnosing whether your bottleneck is in Network/Disk (Log Send Queue) or Secondary Processing/CPU (Redo Queue). The query also calculates an estimated remaining time in seconds to clear the Redo queue.

{% codeblock "sql" %} SELECT ag.name AS availability_group, ar.replica_server_name, d.name AS database_name, drs.role_desc, drs.synchronization_state_desc, -- Log Send Queue: Volume of logs generated on primary awaiting transmission to secondary drs.log_send_queue_size AS log_send_queue_kb, ROUND(drs.log_send_queue_size / 1024.0, 2) AS log_send_queue_mb, drs.log_send_rate AS log_send_rate_kbps, -- Redo Queue: Volume of logs received on secondary awaiting application to MDF file drs.redo_queue_size AS redo_queue_size_kb, ROUND(drs.redo_queue_size / 1024.0, 2) AS redo_queue_size_mb, drs.redo_rate AS redo_rate_kbps, -- Estimated seconds to finish pending application in the Redo Queue CASE WHEN drs.redo_rate > 0 THEN ROUND(drs.redo_queue_size / CAST(drs.redo_rate AS FLOAT), 2) ELSE 0 END AS estimated_redo_completion_seconds, drs.last_redone_time FROM sys.dm_hadr_database_replica_states drs INNER JOIN sys.availability_replicas ar ON drs.replica_id = ar.replica_id INNER JOIN sys.availability_groups ag ON ar.group_id = ag.group_id INNER JOIN sys.databases d ON drs.database_id = d.database_id ORDER BY drs.log_send_queue_size DESC, drs.redo_queue_size DESC; {% endcodeblock %}
