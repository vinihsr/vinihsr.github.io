This article describes one of the most fundamental pillars of modern data infrastructure: replication. Whether to ensure High Availability / Disaster Recovery (HA/DR), relieve the transactional node via Read Scale-Out, or isolate analytical workloads (OLAP), understanding how engines transmit transactions across the network is vital for a DBA/DBRE career.

With that in mind, let's start with the PostgreSQL ecosystem and its two native models:

In Postgres, replication has evolved drastically and is now divided into two well-defined broad categories: Physical replication and Logical replication. Both serve excellent purposes, but work with completely different paradigms under the hood.

1.

Physical Replication (Streaming Replication)

Physical replication operates at the disk block level. The Primary server sends the binary records of its log file (the WAL) byte by byte, in exact chronological order, to one or more secondary servers (Standbys).

Physically, the replica is an identical clone of the primary node. The process works through well-coordinated gears: the primary node runs the walsender process, which pushes the WAL stream over the network to the walreceiver process on the replica. From there, the startup process applies these changes directly to the secondary node's data files (Hot Standby), which remains open exclusively for read queries.

{% figure "/images/postgresql_replicacao_fisica.png", "Diagram of PostgreSQL Streaming Replication Architecture" %}

This model can run in Asynchronous mode (where the Primary confirms the COMMIT without waiting for the replica, creating minimal lag risk) or Synchronous mode (where the Primary holds the COMMIT until the replica confirms writing to the WAL, prioritizing total consistency over network latency).

2. Logical Replication

Introduced in version 10, logical replication abandons physical disk blocks and adopts a Publish-Subscribe model based on table row identities.

The origin node decodes the binary WAL into structured logical commands (e.g., "Insert ID 5 into the Customers table"). This provides fantastic granularity: you can choose to replicate only specific tables, consolidate data from multiple servers into a single analytical Data Warehouse, or perform database version upgrades with practically zero downtime, as it accepts traffic between different Postgres versions.

{% figure "/images/postgresql_replicacao_logica.png", "Diagram of PostgreSQL Logical Replication Publish-Subscribe Model" %}
Fun fact: Unlike the physical standby which is strictly locked as Read-Only, the database subscribing to logical replication accepts local writes and allows the execution of custom triggers during the insertion of replicated data.

After the Postgres overview, we can move on to SQL Server's traditional model:

Here we need to demystify a crucial point. In SQL Server, the term "Replication" refers to a logical object distribution technology based on a subdivision (Publisher, Distributor, and Subscriber) managed via SQL Server Agent. It should not be confused with pure infrastructure and HADR solutions (such as AlwaysOn Availability Groups).

Transactional Replication

This is the most widely used incremental real-time model for Read Scale-Out. The mechanism operates in three fundamental stages:

  • Publisher: The production database that provides the tables (called articles) grouped into a publication.
  • Distributor: The heart of the workflow. It holds a dedicated system database called distribution that temporarily stores commands before final delivery.
  • Subscriber: The destination database that receives and consolidates the transactions.

Under the hood, the Log Reader Agent scans the Publisher's transaction log file (.ldf) looking for modifications to published articles. Upon finding them, it moves the commands to the Distributor. Next, the Distribution Agent takes over the task of unloading and executing these transactions chronologically on the Subscriber.

{% figure "/images/sqlserver_replicacao_transacional.png", "Diagram of SQL Server Transactional Replication Architecture" %}
Critical Difference: While Transactional Replication distributes customizable logical objects (allowing different indexes on the destination), AlwaysOn AG acts physically, transmitting entire transaction log blocks to maintain identical databases at the database level for failover.

Other SQL Server Replication Models

Transactional Replication is the most popular model, but it is far from the only one. SQL Server offers three additional variations, each solving a different topology problem: infrequently changed data, offline devices, and geographically distributed writes.

Snapshot Replication

This is the simplest model of all and, in practice, serves as the baseline to initialize the other two (every Merge or Transactional publication starts with an initial snapshot). Unlike Transactional replication, it does not continuously monitor the transaction log—there is no incremental granularity.

The responsible agent is the Snapshot Agent, which periodically generates a complete copy of the schema and data for published articles, saving .sch (schema) and .bcp (data, via bulk copy) files in the Distributor's snapshot folder. The Distribution Agent then applies this entire copy to the Subscriber, replacing the previous version.

{% figure "/images/sqlserver_replicacao_snapshot.png", "Diagram of SQL Server Snapshot Replication Architecture" %}

Because it does not generate continuous traffic, it is ideal for low-volatility tables (lookup tables, product catalogs) or scenarios where a daily/weekly update window is acceptable.

Merge Replication

Here the pathway ceases to be one-way. Merge Replication allows both the Publisher and Subscribers to make independent changes to the same data—even offline—and synchronize everything later. It is the classic model for field forces (sales reps, technicians) who work disconnected and synchronize upon returning to the network.

The mechanism relies on automated triggers installed on each published table, recording every change in system tracking tables (MSmerge_contents and MSmerge_tombstone), identifying each row by a unique rowguid column. The Merge Agent is responsible for scanning these tracking tables on both nodes and applying pending changes in both directions.

{% figure "/images/sqlserver_replicacao_merge.png", "Diagram of SQL Server Merge Replication Architecture" %}
Fun fact: Because two endpoints can alter the same row simultaneously while offline, Merge requires a conflict resolver. By default, SQL Server uses priority-based resolution (the change from the node with the higher priority number wins), but custom resolvers can be programmed via COM or .NET for specific business rules.

Peer-to-Peer Replication

This is a variation of Transactional Replication designed for multi-master topologies: instead of a single Publisher, all participating nodes simultaneously act as both Publisher and Subscriber to one another. Each node runs its own Log Reader Agent and Distribution Agent, propagating transactions to all other nodes in the mesh.

The goal here is not conflict tolerance (SQL Server does not automatically resolve conflicts in this model), but rather geographically distributed write availability—each region writes locally and replicates to the others, typically with logical data partitioning per node to prevent two endpoints from writing to the same row.

{% figure "/images/sqlserver_peer_to_peer.png", "Diagram of SQL Server Peer-to-Peer Replication Architecture" %}
Golden Rule: Choose the model based on data nature, not tool familiarity. Data that changes rarely and tolerates lag → Snapshot. Data that needs to be edited offline and reconciled later → Merge. Distributed writes with no row overlap between regions → Peer-to-Peer. Real-time reading from a single source of truth → Transactional.

Essential Day-to-Day Monitoring Queries

To mitigate incidents, proactive monitoring of lag and retention states is mandatory. Here are practical starting commands:

For PostgreSQL: Monitoring Replication Lag and Retained Slots

This query calculates the difference in bytes between the current LSN recorded on the Primary and what has already been processed and retransmitted to standbys via the streaming process:

{% codeblock "sql" %} SELECT client_addr AS replica_ip, state, pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn) AS sent_lag_bytes, pg_wal_lsn_diff(sent_lsn, write_lsn) AS write_lag_bytes, pg_wal_lsn_diff(write_lsn, flush_lsn) AS flush_lag_bytes, pg_wal_lsn_diff(flush_lsn, replay_lsn) AS replay_lag_bytes FROM pg_stat_replication; {% endcodeblock %}

To audit the immediate impact of active replication slots and the accumulated disk volume they are forcing the cluster to retain:

{% codeblock "sql" %} SELECT slot_name, slot_type, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal_space FROM pg_replication_slots; {% endcodeblock %}

For SQL Server: Monitoring Log Retention Culprits

If the production transaction log shows unusual growth, run the following diagnostic query to evaluate if Replication or AlwaysOn is preventing file recycling:

{% codeblock "sql" %} SELECT name AS DatabaseName, recovery_model_desc AS RecoveryModel, log_reuse_wait_desc AS LogReuseWaitReason FROM sys.databases WHERE log_reuse_wait_desc IN ('REPLICATION', 'AVAILABILITY_GROUP'); {% endcodeblock %}

If the result returns REPLICATION, it means there are stuck transactions in the log that the Log Reader Agent has not yet been able to read or push to the distribution database. You can complement your investigation by running the DBCC OPENTRAN; command to identify the ID of the oldest active transaction holding the active file pointer.
