The integration of SQL Server with Data Lakes enables the relational engine to access and process distributed data, facilitating the construction of data pipelines in modern architectures. This document details the technical aspects influencing I/O and compute performance in this architecture, alongside presenting technical implementation utilizing CETAS (Create External Table As Select) and OPENROWSET commands.

1.

Internal Architecture and Technical Rationales

Reading and writing data across the network requires optimizations at both the file system and query execution levels to prevent performance degradation on the local database. The choice of file format and the physical data layout are decisive in this process.

  • Advantages of Columnar Storage (Parquet): The Parquet format organizes data in columns rather than rows. This structure facilitates the application of efficient compression algorithms (such as Dictionary Encoding and Run-Length Encoding), substantially reducing storage footprint. Furthermore, it enables columnar projection, where only the columns specified in the SELECT statement are read from disk and transferred across the network.
  • Predicate Pushdown: When executing a query with filters (a WHERE clause) via OPENROWSET, SQL Server has the ability to delegate the evaluation of those filters to the underlying storage layer. Using the metadata present in the footers of the Parquet file's Row Groups (such as minimum and maximum values per block), the engine reads only the blocks that satisfy the query criteria, minimizing the volume of processed data.
  • File Sizing Issues: Processing a large number of small files introduces high system overhead due to the necessity of opening individual HTTP requests, reading each file's metadata, and closing them afterward. To optimize sequential read throughput in object storage, data engineering best practices recommend consolidating Parquet files into sizes ranging between 100 MB and 1 GB.
  • Impact of Data Typing and TempDB Operations: It is imperative to maintain data type consistency between the relational schema and the external file. Typing discrepancies force the SQL Server optimizer to perform implicit casts. This inhibits the ability to apply Predicate Pushdown, resulting in the transfer of the entire dataset across the network into local memory. Consequently, Join or sorting operations that exceed the allocated memory (Memory Grant) will result in Spills to physical disk in the tempdb database, severely degrading performance.

2. Practical Implementation: Access Configuration and CETAS Operations

The process of exporting and reading external data requires the initial configuration of security objects (credentials) and Data Lake mapping. The examples below use generic sales data to illustrate the correct structuring of T-SQL commands.

Step 1: Configuration of Credentials and External Data Source

To enable secure access to Azure Blob Storage or Azure Data Lake Storage, it is necessary to define the database master key, store the access token, and map the root directory in the external data source.

{% codeblock "sql" %} -- 1. Creation of the Database Master Key CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'SuaSenhaComplexaAqui_123!'; -- 2. Creation of the Database Scoped Credential (example using SAS Token) CREATE DATABASE SCOPED CREDENTIAL dl_credential WITH IDENTITY = 'SHARED ACCESS SIGNATURE', SECRET = 'sv=2022-11-02&ss=b&srt=sco&sp=rl&se=2025-01-01T00:00:00Z&st=2024-01-01T00:00:00Z&spr=https&sig=FAKE_SIGNATURE_HASH'; -- 3. Creation of the External Data Source CREATE EXTERNAL DATA SOURCE DS_DataLake_Sales WITH ( LOCATION = 'abs://salesdata@datalakestorage.blob.core.windows.net/2024', CREDENTIAL = dl_credential ); -- 4. Definition of the External File Format CREATE EXTERNAL FILE FORMAT ParquetFF WITH ( FORMAT_TYPE = PARQUET, DATA_COMPRESSION = 'org.apache.hadoop.io.compress.SnappyCodec' ); {% endcodeblock %}

Step 2: Data Export via CETAS

The CETAS operation enables parallel data extraction from the relational database to the Data Lake. The pattern demonstrated below includes the immediate dropping of the local EXTERNAL TABLE object after export, retaining only the physical, consolidated Parquet files in the external storage environment for subsequent analytical use.

{% codeblock "sql" %} --------------------------[ Export: SalesOrder ]-------------------------- CREATE EXTERNAL TABLE Ext_SalesOrder WITH ( LOCATION = 'SalesOrder/', DATA_SOURCE = DS_DataLake_Sales, FILE_FORMAT = ParquetFF ) AS SELECT B.* FROM SalesHeader A INNER JOIN SalesOrderDetail B ON A.OrderID = B.OrderID WHERE YEAR(A.OrderDate) = 2024; -- Removal of the external table metadata (Parquet files remain in the Data Lake) DROP TABLE Ext_SalesOrder; --------------------------[ Export: SystemAuditLog ]-------------------------- CREATE EXTERNAL TABLE Ext_SystemAuditLog WITH ( LOCATION = 'SystemAuditLog/', DATA_SOURCE = DS_DataLake_Sales, FILE_FORMAT = ParquetFF ) AS SELECT A.* FROM SystemAuditLog A WHERE AuditDate >= '2024-01-01 00:00:00' AND AuditDate <= '2024-12-31 23:59:59'; -- Removal of the external table metadata DROP TABLE Ext_SystemAuditLog; {% endcodeblock %}

Step 3: Data Virtualization using OPENROWSET

To query data directly from the Data Lake without needing to physically import it into SQL Server relational tables (preventing unnecessary transaction log growth), the OPENROWSET function is applied.

{% codeblock "sql" %} -- Direct and optimized reading of Parquet files located in the Data Lake SELECT TOP 100 * FROM OPENROWSET( BULK 'SalesOrder/*.parquet', FORMAT = 'PARQUET', DATA_SOURCE = 'DS_DataLake_Sales' ) AS SalesData; {% endcodeblock %}

Isolating workloads via CETAS and OPENROWSET ensures that local transactional workloads (OLTP) are not impacted by reading historical data.
