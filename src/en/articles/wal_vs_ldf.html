This article serves as a practical and theoretical guide regarding log management in database management systems (DBMS), specifically SQL Server and PostgreSQL, which despite sounding similar, follow completely different foundations.

With that in mind, let's start with SQL Server and .ldf files:

Although PostgreSQL physically names its file WAL, this is the name given to the concept, which is also utilized in transaction log files (.ldf). WAL, or Write-Ahead Logging, means that any modification to data or structure is written first to the transaction log on disk before any data page is written to the data file (.mdf). This also serves scenarios where unexpected database crashes occur; SQL Server reads the transaction log during startup and either redoes (redo) or undoes (undo) transactions, aiming to fulfill the "C" in the ACID concept, meaning consistency.

Following the database engine's mechanism premise, we have certain specifications in SQL Server, such as VLFs.

VLF, or Virtual Log Files, theoretically and briefly speaking, are logical partitions within the log file responsible for transactional control at a more granular level. It works circularly, filling VLF 1, VLF 2, VLF 3, and so on until the last one. After the last one, if the first one is already inactive (transaction committed), it overwrites VLF 1.

Fun fact: Poor autogrowth management can generate VLF fragmentation, creating thousands of VLFs per file, destroying recovery performance and degrading write operations.

In addition to these logical partitions, we have recovery models:

The recovery model manages and defines how log growth will happen, along with other HADR-related concepts. To explain what it's about, nothing beats citing the main options (the commonly used ones):

  • SIMPLE: Finished transactions are marked inactive after a CHECKPOINT. The log is truncated (a term used to symbolize that a TRUNCATE command occurs) and reuses space. This prevents the log from growing indefinitely, but sacrifices point-in-time recovery capabilities.
  • FULL: Absolutely everything is logged. A VLF is only marked for reuse after a log backup. If no one performs a log backup, the circular cycle is broken, potentially triggering the dreaded error 9002 and causing the database to halt due to disk exhaustion.

Furthermore, we have a primordial concept: the LSN (Log Sequence Number) which, very directly, works as a locator for your database.

Regardless of the engine, every record entering the log receives this serial number. This is what guarantees that transactions are replayed in the exact order they occurred in the event of a failure.

In SQL Server, it looks like this: 00000032:0000012a:0001

Three blocks meaning: VLF ID, offset within the log block, and transaction slot.

The concept behind log files is complex and full of interesting cases, which will be covered in other articles 100% focused on these scenarios, given that they are long and content-rich subjects on their own.

After an overview of SQL Server log files, we can move on to the database management system WAL in PostgreSQL:

As stated at the beginning, WAL is the name given to the concept, but in Postgres, it also names the file—or rather, the file directory.

Let's go through the physical architecture first:

While SQL Server manages a single file (exemplo.ldf) and divides it logically into partitions, Postgres has a dedicated directory for this called pg_wal (or, in older versions, pg_xlog).

Inside this directory, Postgres creates several physical files with a standard hexadecimal naming convention (000000010000000000000001). By default, each such file is 16MB and is called a WAL Segment.

The circular cycle of SQL Server VLFs occurs here in almost the exact same way, changing only the fact that it involves individual files in a directory rather than partitions of a single file. That is, as transaction writes progress, files are recycled and renamed.

Postgres Recovery Model and its Paradigm:

Here, we do not have FULL or SIMPLE, and this is what the SQL Server DBA needs to understand to avoid getting startled by trying to change the database recovery model via a graphical interface, since management of this feature—like most others—is done globally through the configuration file: postgresql.conf.

wal_level: Defines how much information will be written to the WAL, which can be minimal, replica, or logical:

  • minimal: The minimum required to prevent database corruption during a crash.
  • replica: Sufficient for Point-in-Time Recovery and physical replication.
  • logical: Sufficient for logical replication.

As the equivalent to SQL Server's FULL, you need to enable archive_mode. This makes Postgres execute a script (the archive_command) every time a log file (16MB) fills up, copying it to external storage. Otherwise, if left there, it would sooner or later be recycled.

The LSN (Log Sequence Number) in Postgres is not just a logical sequence, but reads more like a physical position pointer (64-bit byte offset) marking the exact byte of the file where the transaction was recorded.

It looks like this: 16/B374D848

Additionally, Postgres has a native data type exclusively to handle this: pg_lsn.

The CHECKPOINT command was mentioned earlier in SQL Server's SIMPLE recovery model, but it also occurs in Postgres and is a crucial event for WAL health. It is responsible for determining when pages in memory (RAM, Shared Buffers, Cache, etc.) are flushed to disk. Visually speaking, it operates like a supermarket checkout lane, where the CHECKPOINT is the cashier, the files are the customers, and the groceries are the data.

Ok, knowing this, what can cause WAL to impact disk space? In SQL Server, we mentioned cases where disk can be affected by missing configurations. Here, disk impact is typically caused by misconfigured settings, two of which are:

  • Archiving Failure: If the archive_command fails, contrary to what you might think, Postgres does not delete or lose the files; it keeps them locally. Since there is no outflow in this case, logs continue to accumulate, which, with an excess of errors, can impact disk space.
  • Excessively high wal_keep_size: In short, this parameter defines how many gigabytes of WAL the database should retain for safety. Misconfigured, it can consume substantial space and even fill up the disk.

There are replication examples involving WAL not only in Postgres, but the content spans multiple complex topics related to disaster recovery and high availability.

To wrap up, what matters most to us DBAs: queries. Starting with SQL Server:

If you want to check the .ldf size of each database and its usage percentage, you can use:

{% codeblock "sql" %} DBCC SQLPERF(LOGSPACE); {% endcodeblock %}

Meanwhile, this query explains who might be driving unbridled log growth:

{% codeblock "sql" %} SELECT name AS DatabaseName, recovery_model_desc AS RecoveryModel, log_reuse_wait_desc AS LogReuseWaitReason FROM sys.databases WHERE database_id > 4; -- Ignores system databases {% endcodeblock %}

Tip: If the result is LOG_BACKUP, the database is in FULL model waiting for a log backup. If it is ACTIVE_TRANSACTION, someone opened a transaction that hasn't committed yet, alongside other reuse waits.

If you want to monitor VLFs and find out how many exist in the current database to understand internal fragmentation levels (provided your server runs SQL Server 2017 or higher), use this:

{% codeblock "sql" %} SELECT DB_NAME(database_id) AS DatabaseName, COUNT(vlf_sequence_number) AS VLF_Count FROM sys.dm_db_log_info(DB_ID()) GROUP BY database_id; {% endcodeblock %}

Briefly and basically, this will serve for your initial insights. Now we can move on to Postgres:

If your Postgres version is 10+, you don't need to check the log directory via terminal; you can simply run this and list them:

{% codeblock "sql" %} SELECT COUNT(*) AS wal_file_count, SUM(size) / 1024 / 1024 AS total_size_mb FROM pg_ls_waldir(); {% endcodeblock %}

To discover the current WAL segment down to the exact millisecond:

{% codeblock "sql" %} SELECT pg_walfile_name(pg_current_wal_lsn()) AS current_wal_file; {% endcodeblock %}

Since CHECKPOINT only clears WAL data that has already been hardened/committed, long-running transactions can hold onto the WAL and bloat the disk. To inspect them:

{% codeblock "sql" %} SELECT pid, usename AS db_user, client_addr AS client_ip, now() - xact_start AS transaction_duration, query AS executed_query FROM pg_stat_activity WHERE state = 'active' AND xact_start < now() - INTERVAL '5 minutes' ORDER BY transaction_duration DESC; {% endcodeblock %}
