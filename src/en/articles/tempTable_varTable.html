This article serves as a practical and theoretical guide regarding the choice of temporary data structures in SQL Server. Although many developers use Temporary Tables (#table) and Table Variables (@table) interchangeably, they follow completely different foundations and behaviors under the hood.

With that in mind, let's start with Temporary Tables (#table):

A temporary table is a real data structure, physically created in the tempdb database. Just like regular tables, SQL Server can manage and understand what is happening to the data inside it. It exists on disk (or in the buffer cache) and allows you to manipulate massive volumes of information.

Following the database engine's premise, we have certain specifications that give #tables an absurd advantage, such as statistics and histograms.

Statistics, theoretically and briefly, inform the SQL Server optimizer about the quantity and distribution of data (known as histograms). The optimizer has access to this data, reads it all, and consequently builds the best possible execution plan. Additionally, you can create permanent indexes on them, and CPU parallelization works seamlessly.

Fun fact: The OPTION (RECOMPILE) hint works perfectly here, allowing the database to re-optimize the query based on the actual, known data prior to execution.

However, not everything is perfect. Using temp tables generates a slight I/O overhead due to table creation, lock generation, and subsequent dropping. Not to mention, of course, that it occupies real space in tempdb.

After an overview of temp tables, we can move on to Table Variables (@table):

As the name implies, it's just a variable, much like a string or an int. It is initialized, populated, and automatically discarded at the end of the scope or batch.

This might sound like the ideal scenario:

Cleaner syntax (no need to issue a DROP statement) and less metadata I/O generating log traffic in tempdb. However, the paradigm here is extremely dangerous for the database.

SQL Server works blindly with table variables. Regardless of whether you insert 10, 1,000, or 1 million rows, the optimizer will always estimate that there are exactly 100 rows inside (or just 1 in older versions of SQL Server). Simply put, histograms do not exist.

Fun fact: Trying to use OPTION (RECOMPILE) on a table variable won't save your query. Since there are no histograms to read, re-compilation will continue estimating those same 100 rows fixedly.

SQL Server's 30% "Guess":

There is a curious behavior in the SQL Server engine when dealing with Table Variables. Because a @table lacks statistics and histograms, the optimizer remains "blind" to the actual data distribution inside it.

When you run a query using inequality or range operators (such as <, <=, >, >=), the Cardinality Estimation (CE) mechanism needs to guess how many rows will be returned. Without a histogram to read, it applies a fallback rule (a standardized guess): it always estimates that the condition will return exactly 30% of the table's total rows.

Look at the evidence below. We inserted 2,424,830 records into our table variable. When executing a SELECT with the filter WHERE id <= 727450, SQL Server didn't scan the data to find out the answer. It simply took the table's total cardinality and multiplied it by 0.3 (30%). The result? A hardcoded estimate of 727,450 rows.

Excessive Grant and the Feared Spill:

When the database estimates incorrectly (thinking there are 100 rows when there are actually 100k), it consequently gets the RAM memory allocation wrong for executing the operation.

An Excessive Grant occurs when SQL allocates too much memory (wasting vital server resources and preventing other connections from working) or allocates too little memory, based on that fake 100-row estimate.

And what happens if SQL Server allocates too little RAM memory for a heavy sorting operation (Sort)? The data won't fit. As an escape route, the database "spills" (Spill) that operation directly to the hard drive via tempdb. That's when performance plummets, as disk can be thousands to hundreds of thousands of times slower than RAM memory.

To Wrap Up: The Practical Proof of Why Temp Tables Win

So far, we've seen the nightmare a @table can cause in an execution plan. But what if we take the exact same scenario (inserting thousands of rows and performing a sort) and use a #table instead?

{% codeblock "sql" %} CREATE TABLE #MinhaTempTable (id INT PRIMARY KEY, name VARCHAR(50), age INT); -- Inserting the exact same large data volume from the problematic scenario INSERT INTO #MinhaTempTable SELECT id, name, age FROM DEVELOPMENT..proc_1_table_test; -- SQL Server will generate real statistics for this table SELECT id, name, age FROM #MinhaTempTable WHERE id <= 1000 ORDER BY age; DROP TABLE #MinhaTempTable; {% endcodeblock %}

When analyzing the properties of this new query's execution plan, the magic happens. Because SQL Server generates real statistics and histograms for the Temp Table right after data insertion, the optimizer no longer needs to "guess."

In the image below, you can notice that the Estimated Number of Rows matches reality perfectly. Because the database knows the exact amount of data it will process, it allocates memory (Memory Grant) just right and executes the Sort entirely in RAM memory, without any yellow Spill or Excessive Grant warnings:

{% figure "/images/tem_table_image.png", "Execution plan showing accurate estimations with a Temp Table" %}

These are the main practical and theoretical differences between Temp Tables and Table Variables. The golden rule is: if you have fewer than 100 rows (or just a simple parameter passer), a @table can keep your code clean. For any volume beyond that, or if you have doubts about how much your transaction might scale in production, go with a #table. The I/O cost to create it is negligible compared to the architectural nightmare of an execution plan corrupted by a giant variable.
