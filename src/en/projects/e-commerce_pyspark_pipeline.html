This project is an end-to-end data engineering pipeline that simulates the full flow of an e-commerce operation. The architecture was built to orchestrate everything from the generation and ingestion of raw data (simulating "dirty" records) to the delivery of clean, modeled metrics in a relational database (Serving Layer).

Orchestration Flow (Airflow DAG)

The pipeline runs on a fully automated daily schedule managed by Apache Airflow, following these steps:

  1. Ingestion (Raw): Generation of synthetic e-commerce data (orders, events, products) and direct upload to MinIO (a local S3-compatible Data Lake).
  2. Processing and Cleaning: PySpark routines read the raw files, apply schema validations, and clean intentionally corrupted data.
  3. Enrichment and Aggregation: Spark joins the orders tables with product information and calculates primary KPIs (e.g., daily revenue, top products, and retention).
  4. Data Warehouse Load: The aggregated results are ingested into a PostgreSQL database.
  5. Dimensional Modeling: dbt (Data Build Tool) takes over the final transformation, building the staging and marts layers to expose the final tables for analytical consumption.

Tech Stack

  • Apache Spark (PySpark): Data cleaning, enrichment, and heavy aggregations.
  • Apache Airflow: Scheduling, orchestration, and task parallelism.
  • dbt (Data Build Tool): Analytical transformation and documentation in the Data Warehouse.
  • PostgreSQL: Consumption layer (Serving Layer) for the final tables.
  • MinIO: Object storage (local, S3-compatible).
  • Docker Compose: Provisioning and isolation of the entire local infrastructure.

DataOps: Running and Deploying

The infrastructure is provisioned through Docker, ensuring reproducibility. Below are the steps to start the stack.

1. Create the persistence directories and adjust Airflow permissions:

{% codeblock "bash" %} mkdir -p logs/scheduler dags plugins data chmod -R 777 logs data dbt_project echo "AIRFLOW_UID=$(id -u)" >> .env {% endcodeblock %}

2. Download the drivers (JARs) Spark needs to communicate with MinIO (S3) and PostgreSQL:

{% codeblock "bash" %} mkdir -p spark/jars wget https://repo1.maven.org/maven2/org/apache/hadoop/hadoop-aws/3.3.2/hadoop-aws-3.3.2.jar -P spark/jars/ wget https://repo1.maven.org/maven2/com/amazonaws/aws-java-sdk-bundle/1.11.901/aws-java-sdk-bundle-1.11.901.jar -P spark/jars/ wget https://repo1.maven.org/maven2/org/postgresql/postgresql/42.7.3/postgresql-42.7.3.jar -P spark/jars/ {% endcodeblock %}

3. Build and start the containers (open the Airflow UI at localhost:8080 and enable the DAG):

{% codeblock "bash" %} docker compose build docker compose up airflow-init docker compose up -d {% endcodeblock %}

Cloud Readiness

The pipeline was designed with portability to cloud environments in mind. To migrate to AWS, the changes are minimal and configurable through environment variables, with no rewrite of the PySpark code:

  • Replace the MINIO_ENDPOINT URI with the AWS S3 regional endpoint.
  • Inject the AWS IAM Access Keys.
  • Replace the local PostgreSQL connection with the endpoint of an AWS RDS database.
